# AGENTS.md — Go-DDD-Scaffold

A CLI generator (`github.com/Allan-Nava/Go-DDD-Scaffold`) that creates the skeleton of a Go project with a Domain Driven Design layout: the `scaffold init` CLI (`main.go` + `scaffold/`), the generated project's templates (`template/`, `static/`, `module/`, **embedded in the binary**), the `scaffold add module` command, a twin VS Code extension (`extensions/vscode/`), a static site on GitHub Pages (`docs/index.html`, same model as the other projects: no build), GitHub Actions CI (`.github/workflows/`).

This file sets the operating rules for agents (Copilot, Claude, other AI tools) working in this repository. It mirrors [CLAUDE.md](CLAUDE.md): a rule changed there changes here too.

## Working rules (ALWAYS)

- **A template that generates code that does not compile is a blocking bug.** The gate is **`make e2e`**: it generates into a tempdir and runs `go mod tidy && go build ./... && go vet ./... && gofmt -l`. **Always** verify this way, not by reading: the output of `scaffold init` is Go code, not text. `make check && make test` is not enough — the unit tests check syntax and formatting, not compilation against the real dependencies.
- **One set of templates only, and it is the CLI's.** The VS Code extension is a **wrapper** that invokes the `scaffold` binary: it has no templates of its own and must not get them back. It used to have a second set (`extensions/vscode/src/templates/*.tpl` + `scaffold.template.ts`), never read by any code and already drifting from the first — `database/db.tpl` was an identical duplicate of `config/config.tpl`. Removed in the rewrite: if someone proposes "bundling the templates in the extension", that is the regression to refuse. The contract between the two is only the CLI output (`Create`/`Skip` lines, `--version`, exit code): if you change it, update `extensions/vscode/src/scaffold/cli.ts` and its tests.
- **Every commit = an annotated `vX.Y.Z` tag**, without asking: `minor` for substantial changes (new templates/commands/features, removals), `patch` for fixes/dependency bumps. The tag message is the changelog entry: what changes and why, not the list of files. The binary's version comes from `-ldflags "-X main.version=…"` (the workflow takes it from `github.ref_name`): do **not** hardcode it in `main.go`. `version` in `extensions/vscode/package.json` still has to be aligned by hand.
- **What a tag triggers**: `docker-publish.yml` (image on ghcr.io) and `vscode-publish.yml`. `release.yml` instead reacts to a *published release* (or to a manual run with a `tag` input, which also creates the release), not to the tag. It builds the 8 binaries with **`build.sh` from the tag being released**, so a tag older than the build.sh it expects cannot be rebuilt: release a new tag instead. No third-party action: `go-release.action` silently fell back to its own build whenever `build.sh` was not executable in git (mode `100644`), and failed on `BUILD_ARGS` under `set -u` — every release after v0.7.7 broke that way, unseen until 2026-11-06.
- **What decides whether to publish the extension is the `version`, not the tag.** Any tag is a trigger, but the `decide` job queries the public gallery and publishes **only if that version is not online yet**. That is what makes "one tag per commit" compatible with marketplaces where versions are **immutable** and notify users: republishing the same one would fail, publishing a new one on every commit would be spam. So to release the extension it is enough to **raise `version` in `extensions/vscode/package.json`**: the next tag publishes it, the ones after do nothing. Without the `VSCE_PAT` secret (and `OVSX_PAT`, optional) the publish steps are **skipped**, they do not fail.
- **Todo → `docs/backlog.md`** (single source, items with a stable `id`, idempotent sync to GitHub issues). Do not scatter TODOs in the code or the docs. **Milestones are dynamic**: there is no list, there are only the titles written on the items — the sync creates the missing ones on GitHub. ⚠️ If you change `docs/backlog.md` **regenerate `docs/roadmap.md`** (`make roadmap`) and commit it, otherwise the `generated-pages-check` gate fails. Hardening/cleanup items = a backlog entry, do not propose them as "next".
- **Documentation is always in English**: README, `docs/`, the Pages site, audits, backlog items (they become public issues), milestone titles, code comments and script messages.
- **NEVER `git push`** — the user always does it. NEVER `Co-Authored-By` in commits.
- **No binaries in the repo**: CI produces the artefacts. If you find a committed executable, remove it and add it to `.gitignore`, do not update it (there was `scaffold-cli-macos`, 4.8 MB).
- **Zero runtime dependencies on the environment**: `template/` and `static/` are in `embed.FS` (declared in `main.go`, injected as `fs.FS` into `scaffold.Options`). Do not reintroduce lookups on `$GOPATH`, absolute paths or files read from disk at runtime — a `go install`ed binary has no repo next to it.
- **Document factual changes**: `README.md` and `docs/index.html` (generated project tree, installation, flags) must reflect every change to the layout. Non-trivial work → a `.md` doc in `docs/` with an ASCII diagram, like `docs/audit-2026-08-11.md`.

## Pattern for changes to the generator (validated)

1. **Baseline**: `make check && make test && make e2e`. Save the output as it is *before*: it is the reference.
2. **Change** the generator or the templates, one layer at a time (never generator + templates + CI in the same step).
3. **Gate**: `make e2e`. If the set of generated files changes, update the assertion in `main_test.go` (`TestEmbeddedAssetsProduceTheDocumentedLayout`) — it is exact on purpose, not "contains".
4. **Idempotency**: re-running `scaffold init` must not destroy existing files (default: skip; overwriting only with `--force`). Every file goes to a temp file in the same dir and is moved into place only when complete (`rename` with `--force`, hard link without): never write into the destination file directly, or a failed render truncates the user's file.
5. **Functional smoke test** if you touched `template/cmd/`, `template/env/` or `template/database/`: start the generated service **with `APP_ENV=local`** (what `make run` does, so `env/.env.local` is loaded) and check `GET /health` + shutdown on `SIGTERM`, not just compilation. `make e2e` and CI do it; a smoke test with any other `APP_ENV` skips the dotenv file and misses the path users take (that is how a `fatal` on the first `make run` went unseen).
6. **Wrap-up**: align the VS Code extension, README, `docs/`, the extension version, `.gitignore`; then commit.

## Known traps / technical rules

- **Three asset trees, three rules**: `template/` is rendered once by `init`; `static/` is copied byte for byte; `module/` is **one bounded context**, rendered by `init` for the example (`catalog`/`Product`) and by `add module` for each new one, with `__module__` in a path replaced by the module name. Module data: `.Module`, `.ModuleTitle`, `.Entity`, `.EntityVar`, `.Table`. Anything that must exist once per project goes in `template/` (e.g. `cmd/modules.go`, `internal/archtest`); anything per module goes in `module/`.
- **`add module` never edits an existing file**: each module's `cmd/module_<name>.go` registers itself with `register(...)` in an `init()`. Do not replace it with "insert a line into main.go at a marker": that breaks on the first hand edit and makes `add module` non-idempotent.
- **Module templates must be gofmt-clean for any name length**: no column alignment that depends on `{{.Entity}}`/`{{.Module}}` (struct fields, trailing comments, `=` in var blocks). That is why CI, `make e2e` and `TestGeneratedGoFilesAreValidAndFormatted` add a second module with a **multi-word** entity (`InvoiceLine`). And no lists or indented blocks in **doc comments** of templates: `go/format` and `gofmt` rewrite them differently, and the format test fails.
- **The domain imports the standard library only** — in the templates too. `internal/archtest` in the generated project fails otherwise; keep it passing with every template change.
- **`text/template`, NEVER `html/template`**: `html/template` HTML-escapes **Go code** (`&&` → `&amp;&amp;`, `<-` → `&lt;-`) and produces broken sources. It was the reason for the `unescaped` helper and the `data.Quit = "<-quit"` field: workarounds for a bug, not features. Both removed; `TestGenerateDoesNotEscapeGoOperators` is the regression test.
- **`template/` cannot contain a `go.mod`**: it would make the directory a separate module and `//go:embed all:template` would fail with *"cannot embed directory template: in different module"*. That is why the template is called `go.mod.tpl`.
- **Two suffixes, two rules**: `.tmpl` → `.go` (`cmd/main.tmpl` → `cmd/main.go`); `.tpl` → loses the suffix (`go.mod.tpl` → `go.mod`). Files with no suffix in `template/` (`Dockerfile`, `README.md`, `env/.env.local`) still go through the template engine: they can use `{{.ProjectName}}`, but a literal `{{` breaks them. `static/` instead is a byte-for-byte copy, with no rendering — that is where a file with literal `{{` goes.
- **`embed` and dot-files**: the `all:` prefix is needed (`//go:embed all:template`), otherwise `env/.env.local` and `.dockerignore` do not get into the binary.
- **`$GOPATH` is no longer a convention**: the variable is empty on any modern setup (`go env GOPATH` still answers `~/go`). The old `panic("cannot find $GOPATH")` in the package's `init()` made the CLI unusable outside the GOPATH — and the tests passed only because the repo was cloned inside `~/go/src/`. The generation target is **`os.Getwd()`**, not `filepath.Dir(os.Args[0])` (that is the binary's dir — a historical bug: the files ended up next to the executable). The module path is inferred by `scaffold.ModulePath` (git `origin` remote → a **known** code host in the path → legacy `src/` → dir name), not from the GOPATH. Never go back to "any `name.tld` segment is a host": a `first.last` username (`/Users/john.doe/…`) became the module host that way. `--module`/`--name` override the inference; both are validated before the first write.
- **`go build -o scaffold` writes INSIDE `scaffold/`**: Go reads `-o <existing-directory>` as "put the binary there", producing `scaffold/Go-DDD-Scaffold`. Always build into `bin/`. For the same reason **never** a `scaffold` line in `.gitignore`/`.dockerignore`: it would exclude the package.
- **`defer f.Close()` inside a walk callback is a leak**: the defers pile up until the end of the whole walk, not per iteration. Close per file (or in a dedicated closure, as `copyStatic` does).
- **Permissions**: `0o755` for dirs, `0o644` for files. Never `os.ModePerm` (0777).
- **`fs.WalkDir` / `filepath.WalkDir`**, not `Walk` (no `lstat` per entry). And the walk's return value **must be checked**: discarding it hides I/O errors (that was the case of `getTemplateSets`).
- **Never the DSN in logs or errors**: it contains the password. Log host/port/database name.
- **The Go version must be kept in sync in 4 places**: `go.mod`, `Dockerfile`, `template/Dockerfile`, the `go-version` matrix in `go.yml`. The historical drift (`go.mod` 1.19 vs `Dockerfile` 1.18 vs `template/Dockerfile` 1.20) broke the Docker build without breaking CI.
- **Dockerfile: `go mod tidy` in the build is an antipattern** — it needs the network, mutates `go.mod`/`go.sum` and invalidates the layer cache. `COPY go.mod go.sum ./` + `go mod download` as a separate layer **before** `COPY . .`, and a final `alpine` stage (the single-stage `golang:*` image weighed ~1 GB; now 12.2 MB).
- **The CLI version is not a reliable indicator**: the pre-rewrite binary hardcoded `Version: "v1.0.1"` in `main.go`, i.e. a number **higher** than the ones that fixed the bug. An old `go install` leaves that binary in `~/go/bin/Go-DDD-Scaffold` and a minimum-version check would let it through. To tell a usable CLI apart you need a **capability probe**: `init --help` must contain `--force` (a flag introduced by the rewrite). That is what `locateBinary` does, and without it the extension ran the old CLI, which writes next to its own executable instead of into the chosen folder — apparently nothing happened.
- **To try the extension in a real editor** (`@vscode/test-electron`) from inside a session already running in VS Code: remove `ELECTRON_RUN_AS_NODE` (and the `VSCODE_*` variables) from the environment, otherwise the binary starts as node and rejects every flag (`bad option: --user-data-dir`); and `--user-data-dir` must be **short** (e.g. `/tmp/vsc-udd`), because the IPC socket lives inside it and on macOS Unix sockets have a ~104-character limit.
- **GitHub's issue list is eventually consistent**: right after a `POST /issues`, a `GET /issues?labels=…` can return a state a few seconds old. Two runs of `sync-backlog-to-issues.py` a few seconds apart created 2 duplicates exactly this way (#102, #103 — later closed). Do not "fix" it with a sleep: the safety net is the **dedup by `backlog-id`** in the plan (it keeps the issue with the lowest number and closes the others), which makes the sync self-repairing. It applies to anything that reads issues right after writing them.
- **In a workflow `run: cd <dir>` is a no-op**: every step opens a new shell. Use `working-directory` (or `defaults.run.working-directory`).
- **`echo ::set-output` is disabled** by GitHub: for Docker tags/labels use `docker/metadata-action`.
- In tests use `t.TempDir()` (auto-cleanup) and `fstest.MapFS` for the assets: the `scaffold` package tests must not depend on the real `template/` — the end-to-end ones live in `main_test.go`, where the `embed` lives.

- Generated project templates: [template/](template/) (rendered) + [static/](static/) (raw copy). The VS Code extension has no templates of its own: it runs the CLI.
- Dev loop: [Makefile](Makefile) — `check`, `test`, `e2e`, `build`, `docker`, `backlog-lint`, `roadmap`, `backlog-sync[-apply]`
- **Operational backlog**: [docs/backlog.md](docs/backlog.md) (single source) · **Roadmap by milestone**: [docs/roadmap.md](docs/roadmap.md) (**generated**, do not edit it) · tooling: [docs/scripts/](docs/scripts/) — `lib/backlog.py` (parsing + rules, single source), `backlog-lint.py`, `generate-roadmap.py`, `sync-backlog-to-issues.py` (idempotent GitHub issues, milestones created on the fly). The sync touches **only** issues labelled `backlog-sync`: Renovate/Dependabot and third-party reports are never read or closed.
- CI: [.github/workflows/](.github/workflows/) — `go.yml` (gofmt+vet+test matrix 1.22–1.24, **+ a job that compiles the generated project and smoke-tests it**), `release.yml` (8 binaries via `build.sh` → `dist/scaffold_<tag>_<os>_<arch>.tar.gz`/`.zip` + `.sha256`, uploaded with `gh release upload`), `docker-publish.yml` (ghcr.io, multi-arch, GHA cache), `vscode-publish.yml` (marketplace on tag), `pages.yml` (publishes `docs/` as it is; the PNGs in `docs/assets/` are regenerated locally with `scripts/render-assets.sh` from `logo.svg` and `scripts/og-card.html`)
- **Technical audit, fixes and remaining debt**: [docs/audit-2026-08-11.md](docs/audit-2026-08-11.md)
- **Product audit and milestones towards v1**: [docs/audit-2026-11-06.md](docs/audit-2026-11-06.md)
- **VS Code extension** (`extensions/vscode/`): rewritten as a wrapper of the CLI. `src/scaffold/cli.ts` is **pure** — it does not import `vscode` — and that is where the logic lives (binary discovery, argv, output parsing); its tests run with `node --test`, with no editor host (`npm test`). The editor API is only in `extension.ts` and `commands/init.ts`. Zero runtime dependencies: do not add any for convenience. `go install` produces a binary called **`Go-DDD-Scaffold`** (after the module), not `scaffold`: discovery looks for both, and also looks in `$GOBIN`/`$GOPATH/bin`/`~/go/bin` because a GUI editor does not read the shell profile. A same-named program that does not answer `scaffold version` must be discarded, not run. Published on the Marketplace as `allannava95.go-ddd-scaffold`.
- **`node --test <directory>` does not work** on every Node version (on 23.3 it gives `MODULE_NOT_FOUND` on the dir): use the glob `node --test "out/**/*.test.js"`.
- Generated project stack: Fiber v2, GORM (MySQL), zap, `caarlos0/env/v11`, godotenv. DDD layout and its rules: [docs/ddd-guide.md](docs/ddd-guide.md). DI is manual on purpose (Wire is archived): do not add a container.

## graphify

This repo does **not have** a knowledge graph yet. If structural navigation is needed (it is a small repo: ~700 lines of Go + the TS extension), generate it with `graphify build .` and then:

- `graphify query "<question>"` for questions about the code, `graphify path "<A>" "<B>"` for relations, `graphify explain "<concept>"` for specific concepts — they return a scoped subgraph, much smaller than `GRAPH_REPORT.md` or raw grep.
- `graphify-out/wiki/index.md` for broad navigation, `GRAPH_REPORT.md` only for an architectural review.
- After changes to the code: `graphify update .` (AST only, no API cost).
