# Audit di prodotto — 2026-11-06

L'[audit del 2026-08-11](audit-2026-08-11.md) ha reso il generatore **corretto**: la CLI parte
ovunque, il progetto generato compila. Questo audit chiede una cosa diversa: **cosa manca perché sia
un prodotto eccellente**, cioè uno strumento che uno sviluppatore Go sceglie, usa nei primi cinque
minuti senza intoppi e tiene in produzione.

Ogni difetto qui sotto è stato **riprodotto**; i gap di prodotto sono confronti con quello che il
nome e il README promettono. Il piano sta in [`backlog.md`](backlog.md), diviso in milestone, e la
[roadmap](roadmap.md) è rigenerata da lì.

## Baseline

Eseguita sul commit `fbdd72e` (tag `v0.8.4`), Go 1.27.2:

| Gate | Esito |
|---|---|
| `gofmt -l` + `go vet` | ✅ pulito |
| `go test` | ✅ `scaffold/` coperto all'85,6%; `main` allo 0% (solo test sugli asset) |
| `make e2e` (genera, `go mod tidy`, build, vet, gofmt, test) | ✅ |
| `generate-roadmap.py --check`, `backlog-lint` | ✅ |

La base è sana. I problemi sono in quello che il generatore **promette** e in quello che succede
**fuori** dal percorso che la CI prova.

## Difetti verificati

### F1 — Il primo `make run` muore senza MySQL (alta)

Il README del progetto generato dice `make run # listens on :8080` e *"The service starts without a
database when `DB_HOST` is empty"*. Ma `make run` imposta `APP_ENV=local`, che carica
`env/.env.local`, che contiene `DB_HOST=localhost`:

```
$ APP_ENV=local ./svc
{"level":"fatal","msg":"cannot open the database",
 "err":"connect to localhost:3306/dbv: dial tcp 127.0.0.1:3306: connect: connection refused"}
exit 1
```

La CI non lo vede perché lo smoke test gira con `APP_ENV: runner`, cioè **senza** il dotenv: prova
un percorso che nessun utente percorre. È il primo comando che un utente lancia.

### F2 — Module path sbagliato con un punto nel percorso (alta)

`ModulePath` prende il primo segmento che "sembra un host". Un utente macOS o Windows con il nome
`nome.cognome` lo soddisfa:

```
/Users/john.doe/code/svc  →  module john.doe/code/svc     (atteso: svc, o il path del remote)
```

Non esiste un flag per correggerlo: l'unica via è editare `go.mod` e tutti gli import a mano.

### F3 — Nomi di directory non validi producono un progetto rotto (alta)

Il nome del progetto è il nome della directory, usato **senza validazione** in `go.mod`, nel
servizio di `docker-compose.yml`, nel nome del binario del `Dockerfile`:

```
/work/Service Name  →  module Service Name      (go.mod non valido)
                       services: "Service Name:" (nome compose non valido)
```

### F4 — `--force` può cancellare il file dell'utente (media)

Con `--force` il file esistente è aperto con `O_TRUNC`; se il rendering fallisce a metà, il ramo di
errore fa `os.Remove`. Il file originale è già troncato e poi **cancellato**. In più, un errore di
`Flush` lascia su disco un file parziale (il ramo non fa `Remove`). Soluzione: scrivere in un file
temporaneo nella stessa directory e fare `rename` solo a scrittura riuscita.

### F5 — `APP_ENV` ha due default diversi (bassa)

`Configuration.AppEnv` ha `envDefault:"local"`, ma `loadDotEnv` legge `os.Getenv("APP_ENV")` grezzo:
lanciando il binario senza `APP_ENV` la configurazione dice `local` ma `.env.local` **non** viene
caricato.

### F6 — Il progetto generato non ha un `.gitignore` (media)

Il primo `git add .` committa `bin/` e `env/.env.local` (con `API_SECRET` e la password del DB).

### F7 — CORS aperto a tutti di default (media, sicurezza)

`AllowOrigins: "*"` con `Authorization` tra gli header ammessi: il default di un servizio nuovo
dovrebbe essere chiuso e configurabile da ambiente (`CORS_ALLOWED_ORIGINS`).

### F8 — Configurazione dichiarata ma non usata (bassa)

`LOG_LEVEL` non cambia nulla (`zap.NewProduction()` è sempre a `info`); `RUNNING_MODE` e
`API_SECRET` non sono letti da nessun codice. Insieme a `config/config.yml`
([`config-yml-double-source`](backlog.md)) sono quattro manopole finte.

### F9 — Toolchain e immagini a fine vita (media)

| Dove | Oggi | Stato |
|---|---|---|
| `go.mod.tpl`, `Dockerfile` generato, `Dockerfile` della CLI | Go 1.22 | fuori supporto da febbraio 2025 |
| matrice CI | 1.22, 1.23, 1.24 | tutte fuori supporto (oggi: 1.26 e 1.27) |
| immagini runtime | `alpine:3.20` | fuori supporto da aprile 2026 |

Renovate non aggiorna `go.mod.tpl` né le immagini dentro i template, perché non riconosce i file.

### F10 — Distribuzione: binario dal nome scomodo, release ferme (media)

- `go install github.com/Allan-Nava/Go-DDD-Scaffold@latest` produce un binario `Go-DDD-Scaffold`, non
  `scaffold`, perché `main` sta alla radice del modulo.
- I tag arrivano a `v0.8.4`, ma l'ultima **GitHub Release** è `v0.8.2`: le release partono solo da una
  release pubblicata a mano, quindi la pagina "Latest" resta indietro.
- Due percorsi di release in parallelo (già nel backlog: `release-drop-thirdparty-action`).
- Il `Dockerfile` della CLI ha `maintainer` con un indirizzo di lavoro, in un progetto personale.

## Gap di prodotto

### G1 — Il nome promette DDD, il generatore non genera dominio (il gap principale)

Il progetto generato ha `cmd/`, `config/`, `database/`, `env/`: **nessun** livello di dominio,
applicazione o infrastruttura, nessun esempio di entità, value object, repository o caso d'uso. Chi
cerca uno scaffold DDD apre il risultato e non trova quello che il nome promette.

Un prodotto eccellente genera:

```
internal/
├── <modulo>/                 ← un bounded context, uno per cartella
│   ├── domain/               entità, value object, errori, interfaccia del repository
│   ├── application/          casi d'uso (service), dipendono solo dal domain
│   ├── infrastructure/       store GORM che implementa il repository
│   └── transport/http/       handler: traducono HTTP ⇄ casi d'uso
└── archtest/                 test che fallisce se domain importa infrastructure
```

con un modulo di esempio completo e testato, e un comando `scaffold add module <nome>` che ne genera
uno nuovo e lo collega al composition root.

### G2 — Il servizio generato non è pronto per la produzione

Mancano: `/livez` e `/readyz` (oggi `/health` non controlla il database), metriche Prometheus,
request id e tracing OpenTelemetry opzionale, livello di log da ambiente, migrazioni del database,
una CI per il progetto generato, una configurazione `golangci-lint`, test di integrazione.

### G3 — Un solo stack

Fiber + GORM + MySQL, senza alternative. Molti team Go preferiscono la libreria standard (il router
di `net/http` dalla 1.22 basta per la maggior parte dei servizi), PostgreSQL, `sqlc` o `pgx` al posto
di un ORM. Mancano anche `--dry-run` e un modo per vedere cosa verrà generato prima di generarlo.

### G4 — Adozione

README e docs in due lingue mescolate (README in inglese, backlog e audit in italiano), nessuna demo
visiva, nessun progetto d'esempio pubblico, nessun `CONTRIBUTING.md` / `SECURITY.md` / template di
issue. Nessun test "golden" che fotografi l'albero generato completo e ne mostri il diff in review.

## Le milestone

| Milestone | Obiettivo | Quando è finita |
|---|---|---|
| **v0.9 — Primo avvio senza intoppi** | i primi cinque minuti funzionano su ogni macchina | F1–F8 chiusi; lo smoke CI gira con `APP_ENV=local` come l'utente |
| **v1.0 — DDD vero nel progetto generato** | il nome mantiene la promessa | G1: layout a moduli, modulo d'esempio, `scaffold add module`, test d'architettura |
| **v1.1 — Pronto per la produzione** | il servizio generato regge un deploy vero | G2 + F9 |
| **v1.2 — Scelte di stack** | uno strumento per più team | G3: `--http`, `--db`, `--dry-run` |
| **Distribuzione e adozione** | trovarlo, installarlo, fidarsi | F10 + G4 |

L'ordine conta: **v0.9 prima di tutto**, perché un utente che al primo `make run` vede un `fatal`
non arriva a scoprire il resto. **v1.0 è il cuore del prodotto**: senza, il nome è una promessa non
mantenuta.

Gli item già aperti (`config-yml-double-source`, `release-drop-thirdparty-action`,
`pages-config-stale`) restano nelle loro milestone.
