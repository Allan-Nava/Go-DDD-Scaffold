# Product audit — 2026-11-06

The [2026-08-11 audit](audit-2026-08-11.md) made the generator **correct**: the CLI runs anywhere and
the generated project compiles. This audit asks a different question: **what is missing for it to be
an excellent product** — a tool a Go developer picks, gets through the first five minutes with no
surprises, and keeps in production.

Every defect below was **reproduced**; the product gaps compare what exists with what the name and the
README promise. The plan lives in [`backlog.md`](backlog.md), split into milestones, and the
[roadmap](roadmap.md) is regenerated from it.

## Baseline

Run on commit `fbdd72e` (tag `v0.8.4`), Go 1.27.2:

| Gate | Result |
|---|---|
| `gofmt -l` + `go vet` | ✅ clean |
| `go test` | ✅ `scaffold/` at 85.6% coverage; `main` at 0% (asset tests only) |
| `make e2e` (generate, `go mod tidy`, build, vet, gofmt, test) | ✅ |
| `generate-roadmap.py --check`, `backlog-lint` | ✅ |

The base is sound. The problems are in what the generator **promises**, and in what happens **outside**
the path CI exercises.

## Verified defects

### F1 — The first `make run` dies without MySQL (high)

The generated README says `make run # listens on :8080` and *"The service starts without a database
when `DB_HOST` is empty"*. But `make run` sets `APP_ENV=local`, which loads `env/.env.local`, which
contains `DB_HOST=localhost`:

```
$ APP_ENV=local ./svc
{"level":"fatal","msg":"cannot open the database",
 "err":"connect to localhost:3306/dbv: dial tcp 127.0.0.1:3306: connect: connection refused"}
exit 1
```

CI does not see it because the smoke test runs with `APP_ENV: runner`, i.e. **without** the dotenv
file: it exercises a path no user takes. It is the first command a user runs.

### F2 — Wrong module path when the path contains a dot (high)

`ModulePath` takes the first segment that "looks like a host". A macOS or Windows user named
`first.last` satisfies it:

```
/Users/john.doe/code/svc  →  module john.doe/code/svc     (expected: svc, or the remote's path)
```

There is no flag to correct it: the only way out is editing `go.mod` and every import by hand.

### F3 — Invalid directory names produce a broken project (high)

The project name is the directory name, used **without validation** in `go.mod`, in the
`docker-compose.yml` service and in the `Dockerfile` binary name:

```
/work/Service Name  →  module Service Name      (invalid go.mod)
                       services: "Service Name:" (invalid compose service name)
```

### F4 — `--force` can delete the user's file (medium)

With `--force` the existing file is opened with `O_TRUNC`; if rendering fails halfway, the error path
calls `os.Remove`. The original file is truncated first and then **deleted**. Also, a failed `Flush`
leaves a partial file on disk (that path does not `Remove`). Fix: write to a temporary file in the same
directory and `rename` only after a successful write.

### F5 — `APP_ENV` has two different defaults (low)

`Configuration.AppEnv` has `envDefault:"local"`, but `loadDotEnv` reads the raw
`os.Getenv("APP_ENV")`: running the binary without `APP_ENV`, the configuration says `local` but
`.env.local` is **not** loaded.

### F6 — The generated project has no `.gitignore` (medium)

The first `git add .` commits `bin/` and `env/.env.local` (with `API_SECRET` and the DB password).

### F7 — CORS open to everyone by default (medium, security)

`AllowOrigins: "*"` with `Authorization` among the allowed headers: the default for a new service
should be closed and configurable from the environment (`CORS_ALLOWED_ORIGINS`).

### F8 — Configuration that is declared but unused (low)

`LOG_LEVEL` changes nothing (`zap.NewProduction()` is always at `info`); `RUNNING_MODE` and
`API_SECRET` are read by no code. Together with `config/config.yml`
([`config-yml-double-source`](backlog.md)) that makes four fake knobs.

### F9 — End-of-life toolchain and images (medium)

| Where | Today | Status |
|---|---|---|
| `go.mod.tpl`, generated `Dockerfile`, CLI `Dockerfile` | Go 1.22 | unsupported since February 2025 |
| CI matrix | 1.22, 1.23, 1.24 | all unsupported (today: 1.26 and 1.27) |
| runtime images | `alpine:3.20` | unsupported since April 2026 |

Renovate does not update `go.mod.tpl` or the images inside the templates, because it does not
recognise those files.

### F10 — Distribution: awkward binary name, stalled releases (medium)

- `go install github.com/Allan-Nava/Go-DDD-Scaffold@latest` produces a binary called `Go-DDD-Scaffold`,
  not `scaffold`, because `main` sits at the module root.
- Tags reach `v0.8.4`, but the latest **GitHub Release** is `v0.8.2`: releases start only from a release
  published by hand, so the "Latest" page lags behind.
- Two release paths run in parallel (already in the backlog: `release-drop-thirdparty-action`).
- The CLI `Dockerfile` has a `maintainer` label with a work address, in a personal project.

## Product gaps

### G1 — The name promises DDD, the generator generates no domain (the main gap)

The generated project has `cmd/`, `config/`, `database/`, `env/`: **no** domain, application or
infrastructure layer, no example of an entity, value object, repository or use case. Someone looking
for a DDD scaffold opens the result and does not find what the name promises.

An excellent product generates:

```
internal/
├── <module>/                 ← one bounded context per folder
│   ├── domain/               entities, value objects, errors, repository interface
│   ├── application/          use cases (services), depending only on domain
│   ├── infrastructure/       GORM store implementing the repository
│   └── transport/http/       handlers: translate HTTP ⇄ use cases
└── archtest/                 test that fails if domain imports infrastructure
```

with a complete, tested example module, and a `scaffold add module <name>` command that generates a new
one and wires it into the composition root.

### G2 — The generated service is not production ready

Missing: `/livez` and `/readyz` (today `/health` does not check the database), Prometheus metrics, a
request id and optional OpenTelemetry tracing, log level from the environment, database migrations, a
CI for the generated project, a `golangci-lint` configuration, integration tests.

### G3 — A single stack

Fiber + GORM + MySQL, with no alternative. Many Go teams prefer the standard library (since 1.22 the
`net/http` router is enough for most services), PostgreSQL, `sqlc` or `pgx` instead of an ORM. There is
also no `--dry-run`, no way to see what will be generated before generating it.

### G4 — Adoption

Documentation mixes two languages (English README, Italian backlog and audit), there is no visual demo,
no public example project, no `CONTRIBUTING.md` / `SECURITY.md` / issue templates. No "golden" test
captures the whole generated tree and shows its diff in review.

## Milestones

| Milestone | Goal | Done when |
|---|---|---|
| **v0.9 — Smooth first run** | the first five minutes work on every machine | F1–F8 closed; the CI smoke test runs with `APP_ENV=local`, like a user |
| **v1.0 — Real DDD in the generated project** | the name keeps its promise | G1: module layout, example module, `scaffold add module`, architecture test |
| **v1.1 — Production ready** | the generated service survives a real deploy | G2 + F9 |
| **v1.2 — Stack choices** | one tool for more teams | G3: `--http`, `--db`, `--dry-run` |
| **Distribution and adoption** | find it, install it, trust it | F10 + G4 |

Order matters: **v0.9 first of all**, because a user who sees a `fatal` on the first `make run` never
gets to discover the rest. **v1.0 is the heart of the product**: without it, the name is a promise not
kept.

The items already open (`config-yml-double-source`, `release-drop-thirdparty-action`) stay in their
milestones.
