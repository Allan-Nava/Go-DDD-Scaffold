# The generated DDD layout

`scaffold init` generates a service with one example **bounded context**, `catalog`, and
`scaffold add module <name>` adds more. This page explains what goes where and why.

## The layers

```
internal/
├── catalog/                       one bounded context = one folder
│   ├── domain/                    the model: aggregate, value objects, errors, repository port
│   ├── application/               use cases: load → ask the aggregate → save
│   ├── infrastructure/            adapters: GORM store, in-memory store, row ⇄ aggregate mapping
│   └── transport/http/            HTTP ⇄ use cases, domain errors ⇄ status codes
├── billing/                       added with `scaffold add module billing --entity Invoice`
└── archtest/                      fails `go test` when a layer imports what it must not
cmd/
├── main.go                        config, logger, database, HTTP server, graceful shutdown
├── modules.go                     the composition root: mounts every module under /api
├── module_catalog.go              wires catalog: store → service → handler
└── module_billing.go
```

## The dependency rule

Dependencies point **inwards**. The domain is the centre and depends on nothing:

```
   transport/http ──▶ application ──▶ domain ◀── infrastructure
         │                                            ▲
         └──────────── cmd/module_<name>.go ──────────┘
                    (the only file that knows all four)
```

- **domain** imports the standard library and other domains only. No GORM, no Fiber, no zap:
  the business rules can be read, tested and changed without any of them.
- **application** imports the domain. It reaches the database through the `Repository`
  interface that the **domain declares** and infrastructure implements (a *port*): that inversion
  is what lets the arrow from infrastructure point inwards.
- **infrastructure** and **transport** are adapters. They translate — a row into an aggregate, a
  request into a use-case call, `ErrNotFound` into a 404 — and hold no business rule.
- **cmd/** wires the layers by hand. There is no DI framework: one function per module, readable
  top to bottom.

The rule is not left to code review: `internal/archtest` parses the imports of every
`domain` and `application` package and fails when one crosses the line.

```
--- FAIL: TestDependencyRule
    internal/billing/domain/leak.go imports gorm.io/gorm: the domain stays free of third-party code
```

## Where the rules go: rich versus anemic model

Take the rule *"an archived product cannot be renamed"*.

**In the aggregate (rich model)** — what the generated code does:

```go
// domain/model.go
func (e *Product) Rename(name Name, now time.Time) error {
	if e.status == StatusArchived {
		return ErrAlreadyArchived
	}
	e.name = name
	e.updatedAt = now
	return nil
}

// application/service.go
func (s *Service) Rename(ctx context.Context, id, name string) (*domain.Product, error) {
	n, err := domain.NewName(name)          // a Name that exists is valid
	...
	return s.change(ctx, id, func(e *domain.Product, now time.Time) error {
		return e.Rename(n, now)          // the aggregate decides
	})
}
```

The fields are unexported: there is no way to change the name **without** going through the
rule. A second use case that renames — an import, an admin endpoint — gets the rule for free.

**In the service (anemic model)** — the alternative:

```go
// the entity is a bag of public fields
type Product struct {
	ID, Name, Status string
}

func (s *Service) Rename(ctx context.Context, id, name string) error {
	p, _ := s.repo.ByID(ctx, id)
	if p.Status == "archived" {          // the rule lives here...
		return ErrAlreadyArchived
	}
	p.Name = name
	return s.repo.Save(ctx, p)
}
```

It is shorter, and it works — until a second service sets `p.Name` directly and skips the check.
Nothing stops it.

**When each one fits:**

| | Rich aggregate | Anemic entity + service |
|---|---|---|
| The rules | many, they protect state (statuses, limits, totals) | few or none: it is CRUD |
| Who changes the data | several use cases, several teams | one handler |
| Cost | more code per change, methods to design | less code, rules can be bypassed |
| Typical case | orders, policies, subscriptions, invoices | settings, lookup tables, logs |

A project does not have to pick one: choose **per bounded context**. A module that is really CRUD
can keep a thin domain; the generated example shows the rich form because it is the one that is
hard to retrofit.

## Value objects

`Name` is a value object: `NewName` is the only way to build one, and it validates. A function
that takes a `Name` never re-checks it. Add one whenever a primitive carries a rule — an email,
an amount with its currency, a policy number — instead of passing a `string` around and
validating it in three places.

## Testing, layer by layer

| Layer | What the generated tests check | Needs |
|---|---|---|
| domain | invariants: archived is read-only, names are validated, corrupt rows are rejected | nothing |
| application | use cases on the in-memory store, with a fixed clock and ids | nothing |
| infrastructure | the row ⇄ aggregate mapping, the in-memory store keeps copies | nothing |
| transport/http | the HTTP contract: status codes, JSON, error mapping | nothing |
| cmd | every registered module mounts and answers without a database | nothing |
| archtest | the dependency rule | nothing |

None of them needs MySQL. The GORM store is exercised by the service itself when `DB_HOST` is set;
integration tests against a real database are on the [roadmap](roadmap.md) (v1.1).

## Running without a database

With `DB_HOST` empty, every module falls back to its **in-memory** store, logs it, and the service
works — data is lost on restart. Set `DB_HOST` and the same module uses the GORM store and creates
its table (`<module>_<entity>`) with `AutoMigrate`. Versioned migrations are planned for v1.1.

## Adding a bounded context

```sh
scaffold add module billing --entity Invoice
go test ./...
make run
curl -X POST localhost:8080/api/billing -H 'Content-Type: application/json' -d '{"name":"first"}'
```

It generates the four layers, their tests and `cmd/module_billing.go`, which registers itself in
the composition root: **no existing file is edited**. Re-running it skips what exists, like
`init`. To remove a module, delete `internal/billing/` and `cmd/module_billing.go`.

The generated module is a starting point with the shape right, not a finished model: rename
`Name`, add the fields and the rules your context needs, keep them in the aggregate.

## Why no DI framework

The composition root is plain Go: `store → service → handler`, one function per module. Google
Wire, the usual compile-time alternative, was archived in August 2025; runtime containers (`dig`,
`fx`) trade a compile error for a startup error. For a service of this size, explicit wiring is
the more readable option, and it is the one generated.
